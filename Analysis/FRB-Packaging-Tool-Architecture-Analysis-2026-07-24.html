FRB Packaging Tool - Architecture and Flow Analysis

Date: 2026-07-24
Analyst: GitHub Copilot (GPT-5.3-Codex)

Scope and Constraints

  • Analysis covers launcher, engine modules, and config behavior.
  • Master Template is read-only and out of modification scope.
  • GitLab/Okta download flow is treated as deprecated per direction.

Executive Summary

The FRB Packaging Tool is a WinForms orchestration application for creating, validating, and optionally deploying Intune-ready application packages. It is a multi-engine workflow coordinator, not a simple script.

Operational Flow

  1. Launch tool and import engines.
  2. Run first-time setup checks and local path initialization.
  3. Collect metadata and installer media in the GUI.
  4. Create/update package folder from Master Template.
  5. Update Startup.pss and inject custom command sections.
  6. Build Install.exe via SAPIEN command-line tooling.
  7. Run install and uninstall validation loops with technician confirmation.
  8. Generate HTML validation/uninstall reports.
  9. Optionally deploy package to network share.

Active Modules in Current Flow

  • MetadataEngine
  • DetectionEngine
  • ValidationEngine
  • FolderEngine
  • BuildEngine
  • ScanEngine
  • ReportEngine
  • InstallTestEngine
  • PathEngine
  • DeploymentEngine
  • CustomCommandsEngine

Deprecated/Legacy Paths

  • TemplateDownloadEngine (GitLab/Okta)
  • AuthenticationModule (Python/Playwright for GitLab path)
  • GitLabAuthEngine (token storage path)
Direction applied: do not download or depend on GitLab components for future runtime planning.

Risk and What-If Analysis

1) Startup State Drift

If first-run/config flags diverge across local copies, launch behavior can become inconsistent.

2) Path and Naming Assumptions

If base paths are invalid or inaccessible, create/copy/build stages fail downstream.

3) Build Tool Dependency

If SAPIEN command-line build tooling is missing or moved, package creation halts at build stage.

4) Validation Loop Friction

Install/uninstall loops intentionally depend on technician confirmation and can bounce back for manual correction.

5) Deployment Permission Failures

Local success does not guarantee network deployment success if write rights are missing.

Safe Change Zones

  1. Launcher orchestration and event handlers.
  2. Engine modules under src/Engines.
  3. Runtime defaults and flags in config/app.config.json.

Recommended Timeline Strategy

Phase 1 - Stabilize

  • Remove or disable deprecated GitLab/Okta startup paths.
  • Keep local template flow deterministic.

Phase 2 - Harden

  • Improve path/state guardrails and fail-fast messaging.
  • Standardize error handling around create/build/test/deploy transitions.

Phase 3 - Clean and Maintain

  • Separate active modules from backup/legacy variants.
  • Define stable module contracts and regression checks.

Conclusion

The tool has a strong packaging lifecycle foundation. The fastest path to on-time completion is preserving Master Template as-is, removing deprecated GitLab dependencies from startup flow, and stabilizing launcher-to-engine orchestration.
